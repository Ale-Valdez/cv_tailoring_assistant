# CV Tailor - Documentación

Herramienta para adaptar un CV (PDF) a una oferta laboral sin inventar experiencia: analiza la oferta, compara con la experiencia real, detecta keywords ATS, propone cambios revisables y exporta un PDF generado desde HTML.

## Estado actual (dónde quedamos)

- Fecha de última actualización: 2026-11-13
- Fase: **Fase 3 hecha** (sugerencias y revisión). Siguiente: Fase 4, render y exportación.
- Hecho en la Fase 3: `GenerateTailoringProposal` arma un `TailoredCV` para el perfil confirmado y la oferta guardada. Si la instantánea coincide con el perfil actual, no vuelve a llamar al modelo; si el perfil cambió, genera de nuevo, reemplaza las sugerencias y conserva el id. `proposeTailoringGraph` propone cambios de resumen, de bullet o de orden de habilidades. El fabrication guard es determinista, no llama a un LLM, y descarta un texto que introduce una herramienta, una empresa, una cifra o una fecha que el perfil no respalda (tampoco un alias de otro término: `Java` no sale de `JavaScript`). Reintenta hasta 3 veces y tira lo que sigue inválido. Al modelo viaja `profileForModel`, sin contacto (ADR-019), y el texto de la sugerencia no se traduce (ADR-022). Una sugerencia igual al original no se guarda. `POST /jobs/:id/proposals` genera, `GET /jobs/:id/proposal` lee y `POST /proposals/:id/suggestions/:suggestionId/review` acepta, edita o rechaza. Aceptar exige que el guard ya la haya marcado válida. Editar vuelve a correr el guard y, si el texto no se sostiene, no se guarda. Sin pendientes, el estado pasa a `final`. La propuesta queda en PostgreSQL (tabla `TailoredCV`, documento `jsonb`, con los `MatchResult` de esa comparación). La pantalla muestra el antes y el después. Sigue abierto si se puede exportar con sugerencias `pending`. D13, D17 y D19 siguen para la Fase 4: editar una sugerencia es un campo de texto, no el editor del CV.
- Hecho en la Fase 2: `AnalyzeJobPosting` recibe texto pegado (ADR-021), rechaza vacío o de más de 50.000 caracteres y, si el hash ya está guardado, no vuelve a llamar al modelo. `analyzeJobGraph` clasifica requisitos y keywords y reintenta hasta 3 veces. El dominio unifica alias (`Postgres` y `PostgreSQL`, `JS` y `JavaScript`, sin mezclar `Java`) y `matchProfileToJob` marca cada requisito como cubierto, parcial o brecha con bullets de evidencia. Una habilidad sin bullet queda como brecha, con una nota. Las keywords dicen si están en el perfil y, por tanto, si se pueden incorporar. Si el idioma de la oferta y el del perfil difieren, el informe lo avisa y no traduce (ADR-022). `api` expone `POST /jobs/analyze`, `GET /jobs/current`, `GET /jobs/:id` y `GET /jobs/:id/match`. La oferta confirmada por el análisis queda en PostgreSQL (tabla `JobPosting`, documento `jsonb`). El informe no se persiste. La pantalla pega la oferta, muestra requisitos y keywords, y vuelve a comparar sin llamar al modelo.
- Hecho en la Fase 1: `packages/domain` tiene las entidades del modelo, validadas con Zod. El perfil distingue `needs_review` y `confirmed`. Confirmar exige nombre, idioma y los datos mínimos de cada bloque presente. `profileForModel` omite el contacto (ADR-019). Una sugerencia solo sale de `pending` (aceptar, editar o rechazar) y tiene que citar evidencia. Un `TailoredCV` solo admite un perfil ya confirmado. El fabrication guard quedó en la Fase 3. Sigue sin decidirse si se puede exportar con sugerencias pendientes. `ImportProfileFromPdf` (ADR-020) lee el PDF con `unpdf`, rechaza archivos vacíos, de más de 10 MiB o sin texto seleccionable, quita emails y teléfonos antes del extractor, y devuelve un perfil `needs_review` sin bloque de contacto. `ProfileExtractor` lo implementa `extractProfileGraph` en `adapter-ai`: valida el borrador y reintenta hasta 3 veces. El ejemplo de `LLM_MODEL` es `gpt-6-luna` (ADR-011) y deja `LLM_TEMPERATURE` vacío: ese modelo solo acepta la temperatura por defecto. `api` expone `POST /profiles/import`, `POST /profiles/confirm`, `GET /profiles/current` y `GET /privacy`. El proxy de Next.js y Express limitan el PDF a 10 MiB (ADR-017). La pantalla pide confirmación antes de la primera llamada al proveedor y la guarda en el navegador (`cv-tailor.llm-consent`, ADR-019); después se corrige el perfil con formularios. Al confirmar, el perfil queda en PostgreSQL (una fila, documento `jsonb`, ADR-013) y `GET /profiles/current` lo vuelve a mostrar. El PDF original sigue sin `FileStorage`. Detalle del modelo en `03-modelo-de-dominio.md`.
- Hecho en la Fase 0: monorepo pnpm (Node `24.19.0`, pnpm `12.18.0`) y Docker Compose con `web`, `api`, `renderer` y `db` (PostgreSQL 18, volumen `pgdata`). `api` y `renderer` responden `GET /health`. `web` reenvía `/api/*` a `api` y muestra si la API responde. `api` no publica puertos; en desarrollo el override sí. `api` sale al arrancar si faltan `LLM_PROVIDER` (`openai`), `LLM_MODEL`, `OPENAI_API_KEY` o `DATABASE_URL`. Con `LANGSMITH_TRACING=true` también exige `LANGSMITH_API_KEY` y `LANGSMITH_PROJECT`. No hay código de trazas propio: LangSmith traza `extractProfileGraph` cuando el flag está activo (ADR-007). El volumen `files` está montado en `/data/files` (`FILES_DIR`); todavía no hay `FileStorage`. El esquema de Prisma ya guarda el perfil confirmado. `packages/config` queda para cuando haya ESLint compartido.
- Hecho antes del código: análisis, MVP, riesgos, arquitectura, modelo de dominio y decisiones D1 a D10, más D11 (OpenAI), D12 (política anti-invención), D16 (privacidad), D20 (pnpm), D21 (Postgres), D22 (renderer separado), D23 (revisión humana en la aplicación), D24 (verificación de límites) y D25 (proxy web a api con `rewrites`).
- Siguiente: Fase 4, plantilla HTML, vista previa y `ExportTailoredCv`. D13, D17 y D19 siguen abiertas.
- Arranque: copiar `.env.example` a `.env` y completar `OPENAI_API_KEY`. El ejemplo ya trae `LLM_MODEL=gpt-6-luna`. Luego `pnpm compose` (`docker compose up --build`). Antes de confirmar un perfil, analizar una oferta o proponer cambios, con Postgres en marcha: `pnpm db:migrate`. Desarrollo con recarga: `pnpm install` y `pnpm compose:dev`. `pnpm dev` sigue sirviendo las apps en el host (lee `.env`). `pnpm check` ejecuta el typecheck, Vitest y la verificación de límites. El CI hace lo mismo. `dependency-cruiser` usa parser `swc` (`.dependency-cruiser.cjs`, ADR-016) porque la versión 18 no lee TypeScript 7, y no analiza los `*.test.ts`. `pnpm boundaries` falla si el parser no pudo leer los fuentes.

## Resumen de la arquitectura

Monorepo TypeScript (pnpm workspaces) con arquitectura hexagonal. Backend Express (`apps/api`), frontend Next.js solo UI (`apps/web`), servicio `renderer` con Playwright y base PostgreSQL, todo con Docker Compose. LangChain y LangGraph orquestan los LLM dentro del adaptador de IA; el proveedor es OpenAI y se cambia desde el `.env` mediante una fábrica de modelos. LangSmith se activa solo con variables de entorno. Un solo usuario local, sin login.
